# Architecture

## Goals

`securecrt-mcp` is designed around one constraint: SecureCRT's `crt` object is available only to scripts executed by SecureCRT itself. The MCP process therefore cannot be the component that directly calls SecureCRT APIs.

The project splits responsibilities into two trust domains.

## Rust MCP server

Responsibilities:

- MCP transport and tool definitions
- input validation
- local command policy
- audit logging
- bridge authentication
- timeout and request-size enforcement
- client-facing errors

The MCP server does not contain SSH protocol logic and does not parse SecureCRT credential stores.

## SecureCRT Python bridge

Responsibilities:

- run inside SecureCRT
- enumerate tabs with `crt.GetTabCount()` / `crt.GetTab()`
- inspect `tab.Session.Connected`
- read visible terminal text with `tab.Screen.Get2()`
- send text using `tab.Screen.Send()`
- optionally capture output with `tab.Screen.ReadString()`
- activate a tab with `tab.Activate()`

The bridge intentionally contains no MCP implementation and no command authorization policy. Keeping authorization in Rust makes it easier to test and evolve without coupling security decisions to SecureCRT's scripting runtime.

## Local bridge transport

The first implementation uses newline-delimited JSON over a TCP listener bound to `127.0.0.1`.

Reasons:

- Python standard library only
- available on Windows, macOS, and Linux
- easy to implement inside SecureCRT without external packages
- easy to inspect and version
- keeps SecureCRT API calls on the same script thread

Every request includes a random token generated by `securecrt-mcp init`.

## Why not a background Python thread?

SecureCRT scripting APIs are application automation objects. The bridge keeps socket polling and `crt` API access in one script loop rather than invoking `crt` from an arbitrary worker thread. This reduces thread-affinity and reentrancy risk.

The listening socket uses a short timeout, followed by `crt.Sleep()`, so the script can keep servicing the SecureCRT event loop.

## MCP transport

The MCP-facing process uses the official Rust MCP SDK (`rmcp`) and stdio transport. Stdio is the simplest and most widely supported local MCP transport for desktop clients.

Future versions may add Streamable HTTP behind an explicit opt-in configuration, but remote exposure is not a v0.1 goal.

## Command execution modes

### Screen snapshot

1. Send command plus carriage return.
2. Wait for `settle_ms`.
3. Capture the visible terminal screen with `Get2()`.

This is generic and works across many shells and network devices, but it is not a strict command-completion primitive.

### wait_for

1. Set `Screen.Synchronous = True`.
2. Send command.
3. Use `Screen.ReadString(wait_for, timeout)`.
4. Restore `Synchronous`.

Use this when a predictable prompt or marker is available.

## Future backend abstraction

The bridge protocol is intentionally independent of Python. A future backend could be:

- an official VanDyke external automation API
- a native SecureCRT plugin/API if one is introduced
- a platform-specific automation adapter
- a multi-process bridge registry

The MCP tool names can remain stable while backend capabilities evolve.
